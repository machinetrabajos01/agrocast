Saved model and preprocessing

  • models/sarima_v{{ versions[-1] }}.joblib: specification and frozen parameters for the three series, training cut-off, data fingerprint, preprocessing steps and the reference distribution used by the drift check.
  • models/sarima_v{{ versions[-1] }}.json: model card (selection rule, metrics, coverage, orders and AICc).
  • Versions available: {{ versions|join(', ') }}. The administrator activates a version in the information system; every inference stores the version used.
  • Preprocessing at inference (src/inference.py) repeats the training steps: monthly frequency, gap and range checks, logarithm, back-transformation with the exponential.
  • Rebuild: python -m src.pipeline, then python -m src.train_model --version {{ versions[-1] }}.

Inputs, outputs and dependencies

InputSeries (total, fertilizer or pesticide), horizon 1–6, monthly history of at least 36 consecutive positive values
OutputForecast path, 80% and 95% ranges, expected change, recommendation (buy now / defer / as planned), confidence, model version, compute time
Rejected inputGaps, non-positive values, unknown series, horizon out of range (HTTP 422, logged)
APIPOST /api/v1/forecast with JSON {"series": "total", "horizon": 6} (signed-in analyst or administrator)
DependenciesPython 3.13, Flask 3, statsmodels 0.15, pandas, numpy, joblib, Flask-SQLAlchemy, psycopg, gunicorn (requirements.txt)
Run locallypip install -r requirements.txt → flask --app app init-db → flask --app app seed → flask --app app run

Initial user instructions

  1. Read the forecast together with its 80% range; when the range crosses zero the signal is weak.
  2. "Buy now" means the index is expected to rise more than 3% within the horizon; "Defer" means a fall of more than 3%; otherwise keep the plan.
  3. The index is national. Check the product price of your department in the Market pages before buying.
  4. Producers use the model inside their purchase plans: create a plan, add products, press Evaluate with model, then record the decision.
  5. Report anything unexpected in Support & Feedback.

Full guides in the repository: docs/user_manual.md and docs/training_guide.md.

Monitoring, incident reporting and user feedback

  • Monitoring: every inference, rejected input, slow request (> 3 s) and server error is stored in the operational log; the analyst reviews the Model monitoring page (forecast vs actual, drift checks).
  • Incident reporting: any signed-in user opens a report in Support & Feedback (type bug, data_issue, model_issue or access; severity; description). States: open → in progress → resolved → closed.
  • Feedback: the same module has the "feedback" type; reports are reviewed weekly and prioritized into the next version.
  • Response targets: high severity the same business day, medium 2 business days, low at the weekly review (docs/support_procedures.md).
