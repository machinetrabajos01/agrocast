System design

Users, business processes, requirements, business rules, architecture, database model and the place of machine learning in the workflow.

Business processes

  1. Farm management — register, edit and remove production units.
  2. Input purchase planning — draft plan → products priced with SIPSA-I → model evaluation → decision (approve / defer) → purchase with actual prices → closed. Plans can be cancelled while open.
  3. Index data management — register each new UPRA month, correct values, keep the series continuous.
  4. Support — incidents and feedback: report → assign → in progress → resolved → closed.
  5. Model operation — inference history, forecast vs actual, drift checks, version activation, user administration.

Functional requirements

  • FR1 Registration, login and logout with hashed passwords.
  • FR2 Role-based authorization enforced on the server.
  • FR3 CRUD of farms, purchase plans and plan items.
  • FR4 Evaluate a plan with the production model and show the recommendation, projected cost, interval, meaning and limitations.
  • FR5 Record the decision and the actual purchase.
  • FR6 Store every inference with date, user, input, result, model version and response time.
  • FR7 CRUD of index observations (analyst).
  • FR8 Forecast lab and JSON API with stored or scenario inputs.
  • FR9 Monitoring: response times, errors, forecast vs actual, drift checks.
  • FR10 Indicators and CSV export.
  • FR11 Incident and feedback management.
  • FR12 User, role and model version administration.

Business rules

  • BR1 Self-registration always creates a producer; any role sent by the client is ignored.
  • BR2 Only administrators change roles or disable accounts, never their own.
  • BR3 Producers only see and modify their own farms, plans, inferences and reports.
  • BR4 The purchase month must be within the six months after the latest official index month.
  • BR5 Item prices come from the latest SIPSA-I record, not from the user.
  • BR6 A plan needs at least one item to be evaluated; changing items or the month returns it to draft.
  • BR7 A decision requires a current evaluation with the active model version; a decision different from the model requires a justification.
  • BR8 Only approved plans can be closed as purchased, and all actual prices are required.
  • BR9 Approved or closed plans cannot be edited; only draft or cancelled plans can be deleted; farms with plans cannot be deleted.
  • BR10 Index values must be positive, monthly and continuous; only the latest month can be deleted.
  • BR11 Exactly one model version is active at a time.
  • BR12 Incidents can only be resolved or closed with a written resolution.

Where machine learning contributes

The model supports one decision of the purchasing process: when to buy the inputs of a plan. When the producer evaluates a plan, the server maps the plan category to the fertilizer or pesticide index, computes the horizon between the latest official month and the purchase month and runs SARIMA on the stored records.

  • Expected rise ≥ 3% → Buy now to protect the budget.
  • Expected fall ≥ 3% → Defer purchase; the plan stays open for re-evaluation.
  • Otherwise → Buy as planned.

The forecast change is applied to the plan cost to obtain the projected cost and an 80% range. The decision is recorded next to the recommendation, which allows measuring how often the model is followed and comparing projected and actual costs.
